

1. **Backend:** один `QuizRestController`, который принимает HTTP-запросы, вызывает существующий `QuizApplicationService` и возвращает ответы.
2. **BackendRestClient:** отдельный компонент, который отправляет HTTP-запросы к Backend. Желательно оформить его в JAR, чтобы его можно было подключать к другим Java-приложениям.
3. **Client:** консольное приложение, которое взаимодействует с пользователем и использует `BackendRestClient` для общения с Backend.

# 3. Распределение ответственности между участниками

| Участник | Основная зона ответственности | Что реализует | Что тестирует |
|---|---|---|---|
| Участник 1 | Backend | `QuizRestController`, DTO, обработку HTTP-запросов и ошибок | Контроллер и взаимодействие контроллера с `QuizApplicationService` |
| Участник 2 | BackendRestClient | HTTP-клиент, методы для обращения к Backend, сборку JAR | Методы клиента, отправку запросов и обработку ответов |
| Участник 3 | Client | Консольное приложение, обработку пользовательского ввода и диалога | Обработку сообщений, переходы между состояниями диалога |

### Участник 1. Backend и RestController

Его задача — сделать существующий Backend доступным через HTTP.

Что нужно реализовать:

- Один `QuizRestController` с необходимыми endpoint'ами.
- DTO — объекты, которые определяют структуру запросов и ответов.
- Преобразование входящих HTTP-запросов в вызовы методов `QuizApplicationService`.
- Преобразование результатов работы сервиса в HTTP-ответы.
- Обработку некорректных запросов и ошибок.

Например, если пользователь хочет начать квиз, Backend должен получить запрос, извлечь из него необходимые данные, вызвать `QuizApplicationService` и вернуть результат в JSON.

**Тесты:**
- Контроллер правильно обрабатывает запрос на начало квиза.
- Контроллер правильно обрабатывает отправку ответа.
- Контроллер корректно возвращает результаты завершения квиза.
- Некорректные запросы обрабатываются ожидаемым образом.
- Данные, возвращаемые контроллером, соответствуют ожидаемому формату.

Для тестирования контроллера можно использовать Spring MockMvc. Он позволяет проверять HTTP-запросы и ответы, не запуская полноценный сервер.

### Участник 2. BackendRestClient и JAR

Это отдельная и достаточно самостоятельная задача.

Нужно создать компонент `BackendRestClient`, который будет предоставлять удобные методы для общения с Backend.

Например:

- `startQuiz(...)` — отправить запрос на начало квиза;
- `sendAnswer(...)` — отправить ответ пользователя;
- `finishQuiz(...)` — завершить квиз;
- `abortQuiz(...)` — прервать квиз;
- `getLeaderboard(...)` — получить таблицу лидеров.

Внутри этих методов будет использоваться Spring `RestClient`, который непосредственно выполняет HTTP-запросы.

Важно разделять два понятия:

- **Spring `RestClient`** — готовый инструмент Spring для отправки HTTP-запросов.
- **Ваш `BackendRestClient`** — собственный класс, который скрывает детали HTTP-взаимодействия и предоставляет понятные методы для других приложений.

Например, Client не должен самостоятельно формировать HTTP-запросы, разбираться в адресах endpoint'ов и преобразовывать JSON. Он просто вызывает `backendRestClient.startQuiz(...)` и получает результат.

#### Попытка упаковать BackendRestClient в JAR

Я бы действительно включил это в текущую задачу, а не оставлял на потом. Это даст вам практический опыт создания подключаемой Java-библиотеки.

Предлагаю следующий порядок:

1. Сначала реализовать `BackendRestClient` в отдельном проекте или модуле.
2. Определить, какие классы необходимы для его работы: сам клиент, DTO запросов и ответов, настройки подключения.
3. Настроить сборку JAR.
4. Подключить полученный JAR к проекту Client.
5. Проверить, что Client может использовать методы `BackendRestClient` и успешно общаться с Backend.

**Важное уточнение:** JAR должен содержать не только класс `BackendRestClient`, но и необходимые для его работы классы, например DTO. Также нужно учитывать внешние зависимости: Spring-библиотеки, используемые клиентом, должны быть доступны проекту, который подключает JAR. Обычный JAR не обязательно содержит их внутри.

Если не получится собрать и подключить библиотеку в рамках отведённого времени, используйте запасной вариант: перенесите `BackendRestClient` и необходимые DTO непосредственно в проект Client. Но саму попытку сборки JAR я бы не исключал.

**Тесты:**
- Проверить, что `startQuiz()` формирует правильный запрос.
- Проверить, что клиент корректно преобразует JSON-ответ в Java-объект.
- Проверить обработку ошибок HTTP.
- Проверить остальные методы клиента.

Для тестирования можно использовать `MockRestServiceServer` — инструмент Spring, позволяющий проверять HTTP-взаимодействие без необходимости запускать настоящий Backend.

### Участник 3. Client и обработка диалога

Его задача — реализовать консольное приложение, которое взаимодействует с пользователем.

Client не должен знать, как устроен Backend и как работает `QuizApplicationService`. Он должен обращаться к Backend исключительно через `BackendRestClient`.

Что нужно реализовать:

- Чтение сообщений пользователя из консоли.
- Определение того, какое действие пользователь хочет выполнить.
- Вызов соответствующего метода `BackendRestClient`.
- Отображение полученного ответа.
- Управление последовательностью действий в диалоге.

Например:

1. Пользователь вводит команду `/start`.
2. Client вызывает `backendRestClient.startQuiz(...)`.
3. Backend обрабатывает запрос и возвращает первый вопрос.
4. Client отображает вопрос и варианты ответов.
5. Пользователь вводит ответ.
6. Client вызывает `backendRestClient.sendAnswer(...)`.
7. Получает следующий вопрос или результат.

Я бы рекомендовал выделить отдельный класс `DialogHandler`, который будет отвечать за логику диалога. Тогда консольное приложение будет заниматься преимущественно вводом и выводом, а `DialogHandler` — определять, что делать с сообщениями пользователя.

**Тесты:**
- Пользователь начинает квиз — Client обращается к нужному методу клиента.
- Пользователь отправляет ответ — Client получает и отображает результат.
- Пользователь завершает или прерывает квиз.
- Client корректно обрабатывает ответы Backend и ошибки.

# 4. Как организовать совместную работу

### День 1. Общее проектирование

Все трое вместе:

1. Изучают существующий `QuizApplicationService` и его методы.
2. Определяют, какие действия пользователь сможет выполнять через HTTP.
3. Согласовывают endpoint'ы.
4. Определяют структуру JSON-запросов и ответов.
5. Согласовывают DTO, которые потребуются Backend и BackendRestClient.

Например, можно начать с такого API:

| HTTP-метод | Endpoint | Назначение |
|---|---|---|
| POST | `/api/quizzes/start` | Начать квиз |
| POST | `/api/quizzes/answer` | Отправить ответ |
| POST | `/api/quizzes/finish` | Завершить квиз |
| POST | `/api/quizzes/abort` | Прервать квиз |
| GET | `/api/leaderboard` | Получить таблицу лидеров |
| GET | `/api/users/{id}/record` | Получить личный рекорд |

Это предварительный вариант: окончательный список нужно сверить с возможностями существующего `QuizApplicationService`.

Результат первого дня — небольшой документ `API.md`, в котором описаны все запросы и ответы. Например:

**Запрос на начало квиза:**

```json
{
  "userId": 123456,
  "questionCount": 5
}
```

**Ответ:**

```json
{
  "sessionId": 1,
  "question": {
    "id": 10,
    "text": "Какой бог был богом грома в скандинавской мифологии?",
    "answers": [
      {
        "id": 1,
        "text": "Один"
      },
      {
        "id": 2,
        "text": "Тор"
      }
    ]
  }
}
```

Это только иллюстрация: названия полей и классов нужно согласовать с вашей существующей моделью.

### День 2. Первый сквозной сценарий

На второй день нужно добиться самого важного результата: **Client отправляет HTTP-запрос, Backend его обрабатывает, вызывает `QuizApplicationService` и возвращает JSON, который Client может прочитать.**

Каждый участник работает над своей частью:

- Участник 1 создаёт минимальный `QuizRestController` с endpoint'ом начала квиза.
- Участник 2 создаёт минимальный `BackendRestClient` с методом `startQuiz()`.
- Участник 3 создаёт минимальный Client, который принимает команду пользователя и вызывает `startQuiz()`.

Не нужно сразу реализовывать все функции. Сначала добейтесь работы одного сценария от начала до конца.

### Дни 3–4. Реализация остальных функций

- Участник 1 добавляет остальные endpoint'ы и обработку ошибок.
- Участник 2 реализует остальные методы `BackendRestClient`, начинает сборку JAR и проверяет подключение.
- Участник 3 реализует полноценную логику диалога и консольный интерфейс.

В эти дни участники должны регулярно проверять совместимость своих частей.

### День 5. Тестирование компонентов

Каждый пишет тесты для своей зоны ответственности.

Важно не откладывать тестирование до самого конца: тесты помогут обнаружить несоответствия между компонентами.

### День 6. Интеграция

Все трое вместе проверяют полный сценарий:

1. Пользователь запускает Client.
2. Начинает квиз.
3. Получает вопросы.
4. Отвечает на них.
5. Завершает квиз.
6. Получает результат.
7. Проверяет таблицу лидеров.

Здесь важно проверить не только успешный сценарий, но и ошибки: например, пользователь отправляет некорректный ответ или пытается выполнить действие без активного квиза.

### День 7. Проверка независимости диалогов

Это особенно важная часть вашей задачи.

Представьте, что два пользователя одновременно общаются с ботом:

- Пользователь A начинает квиз.
- Пользователь B начинает квиз.
- Пользователь A отвечает на вопрос.
- Пользователь B отвечает на свой вопрос.
- Пользователь A продолжает квиз.

Диалог одного пользователя не должен влиять на диалог другого.

Для этого Backend должен хранить состояние квиза отдельно для каждого пользователя. Нельзя, например, просто создать поле `currentQuiz` в контроллере или сервисе, которое будет перезаписываться при каждом новом запросе.

Проверьте это отдельным тестом, в котором действия двух пользователей чередуются.

### День 8. Сборка JAR и проверка подключения

Если к этому моменту JAR ещё не готов:

- проверьте, что библиотека собирается;
- проверьте, что Client может подключить её;
- убедитесь, что все необходимые классы и зависимости доступны;
- запустите сквозной сценарий с использованием JAR.

Если возникли проблемы, которые не удаётся решить быстро, используйте запасной вариант с переносом `BackendRestClient` в Client.

### Дни 9–10. Финальная проверка

- Исправление ошибок.
- Повторный запуск всех тестов.
- Проверка сборки Backend и Client.
- Проверка инструкций по запуску.
- Подготовка демонстрации проекта.

Если у вас только неделя, объедините некоторые этапы, но не отказывайтесь от ранней интеграции и проверки независимых диалогов.

# 5. Как организовать GitHub

Я бы предложил использовать следующую структуру веток:

- `main` — стабильная версия проекта.
- `dev` — общая ветка разработки.
- `feature/rest-controller` — работа над контроллером.
- `feature/backend-rest-client` — работа над клиентской библиотекой.
- `feature/console-client` — работа над консольным приложением.

Каждый участник работает в своей ветке и создаёт Pull Request в `dev`.

В Pull Request желательно указывать:

- Что реализовано.
- Какие тесты добавлены.
- Какие тесты успешно прошли.
- Что пока не реализовано.
- Какие изменения могут потребовать внимания других участников.

Не стоит сливать большие объёмы кода в последний день. Лучше создавать небольшие Pull Request по мере готовности отдельных функций.

# 6. Как сделать так, чтобы все трое понимали весь проект

**Правило 1. Каждый участник пишет и функциональный код, и тесты.**

**Правило 2. Каждый должен понимать полный путь запроса.**

Каждый участник должен уметь объяснить следующую цепочку:

```text
Пользователь
    ↓
Console Client
    ↓
DialogHandler
    ↓
BackendRestClient
    ↓
HTTP-запрос
    ↓
RestController
    ↓
QuizApplicationService
    ↓
Domain и Repository
    ↓
HTTP-ответ
    ↓
BackendRestClient
    ↓
DialogHandler
    ↓
Console Client
    ↓
Пользователь
```

**Правило 3. Проводите взаимное ревью.**

Например:

- Участник 1 проверяет код участника 2.
- Участник 2 проверяет код участника 3.
- Участник 3 проверяет код участника 1.

Это позволит каждому познакомиться с чужими частями проекта.

**Правило 4. Каждый должен хотя бы один раз запустить и отладить чужой компонент.**

Например, участник, который занимался контроллером, должен попробовать запустить Client и проследить, как запрос доходит до Backend. Это гораздо полезнее, чем просто прочитать чужой код.

# 7. Что я считаю наиболее важным при вашем сроке

Я бы расставил приоритеты следующим образом:

| Приоритет | Результат |
|---|---|
| Обязательно | Рабочий `QuizRestController`, связанный с `QuizApplicationService` |
| Обязательно | Рабочий `BackendRestClient`, отправляющий HTTP-запросы |
| Обязательно | Консольный Client, использующий `BackendRestClient` |
| Обязательно | Независимые диалоги нескольких пользователей |
| Обязательно | Тесты всех трёх компонентов |
| Желательно | Упаковка `BackendRestClient` в JAR и подключение к Client |
| Желательно | Полная интеграционная проверка всего сценария |

**Моя главная рекомендация:** не пытайтесь сначала полностью реализовать Backend, затем полностью Client, а потом соединить их. Это слишком рискованно для срока в 1–2 недели. Уже на второй день у вас должен работать хотя бы один сквозной сценарий.

И ещё: не воспринимайте JAR как отдельную большую задачу, которую нужно выполнить любой ценой. Это полезный архитектурный и учебный результат, но если сборка библиотеки начнёт угрожать готовности основной функциональности, лучше временно встроить `BackendRestClient` в Client. Тогда вы всё равно получите работающий проект, а опыт упаковки сможете закрепить на уже готовом коде.
